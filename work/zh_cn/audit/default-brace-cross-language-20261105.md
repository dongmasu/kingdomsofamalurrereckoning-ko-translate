# default 중괄호 문법 다국어 교차 검수

## 범위와 방법

- 2026-11-05 기준 `src/csv/{en_us,ja_jp,zh_cn,de_de,fr_fr,es_es,it_it,ru_ru}/`의 `default` 원본 8종과 `work/zh_cn/locatexts_zh_cn.koalocatext_default.csv`의 한국어 작업본을 비교했다.
- 각 파일을 UTF-8 BOM 및 세미콜론 CSV로 읽고, 줄바꿈이 포함된 필드까지 파싱했다. 9개 파일 모두 중복 없이 65,135개 레코드이며 ID 집합이 같다.
- 같은 ID의 전체 텍스트에서 `{숫자}`, `{*한 자리 숫자...}`, `{LINE_...}`를 추출해 순서와 출현 횟수를 비교했다. `{*120分钟}`처럼 번호 바로 뒤에 숫자로 시작하는 텍스트가 붙기 때문에 `120`을 번호로 읽지 않았다. 한 자리라는 것은 이 자료에 대한 파싱 가정이지 런타임 규격의 증명은 아니다.
- 추가로 모든 `{`와 `}`의 균형 및 위 패턴으로 분류되지 않는 시작 부분을 확인했다. 균형이 맞는 것만으로 올바른 문법이라고 단정하지 않는다.
- 전수 비교는 토큰의 문자열과 빈도에 관한 것이며, 모든 차이를 오류라고 판정한 것은 아니다. 아래 예시는 같은 ID의 문맥을 확인해 분류했다. 실제 게임 코드와 화면은 확인하지 못했다.

## 유추한 규칙

### `{1}`, `{2}`: 동적 값 자리

- `565`: `Your {1} has been buffed by {2} points.`에서 `{1}`은 능력치, `{2}`는 증가량으로 읽힌다. `2334`의 `{1}`은 카메라를 조작하는 입력에 해당한다. **번호의 뜻은 문장마다 다르다.**
- `565`의 이탈리아어는 `{2}`가 `{1}`보다 먼저 나온다. 한국어도 어순에 따라 순서를 바꿀 수 있다. 다만 각 번호를 임의로 바꾸거나 빠뜨리지 말고, 해당 ID의 의미와 출현 횟수를 함께 확인한다.
- 같은 인자를 여러 번 쓰는 경우가 있다. `45354`에는 목표 수 `{2}`와 진행도 `{1}/{2}`가 있다. 러시아어는 첫 `{2}`를 생략하지만 진행도에는 유지한다. 따라서 누락이 곧 실행 오류라는 증거는 아니며, 목표 수의 정보가 다른 부분에 남는지도 따져야 한다.
- `30125`, `38383` 등은 영어 자체에 `{3}`이 두 번 나온다. 독일어는 한 번만 쓰고 뜻을 간소화한다. 이 중복이 실제 게임 효과의 확률 구조를 정확히 나타내는지는 문자열만으로 확정할 수 없다.
- 자동 치환인지, 인자의 자료형이나 번호별 공통 의미가 무엇인지는 런타임 미확인이다.

### `{*N문구}`: 표시 서식 후보

- `{*1abilities}`, `{*2Weapon Factors}`처럼 내부는 번역되는 표시 문구다. `5451`은 `{1}` 버튼 인자와 `{*1abilities}`를 함께 사용한다.
- `{*1{2}}`처럼 안에 동적 인자가 들어갈 수 있다. `24`의 `Health: {1}/{*1{2}}`가 예다. 번역할 때 바깥 서식과 안쪽 인자를 구별한다.
- `41237`은 `{*2greens}`, `{*3blues}`, `{*4purples}`, `{*5golds}`로 아이템 이름의 색을 설명한다. `51803` 개발용 문자열에는 `{*6 ... RED}`와 `{*4 ... green}`이라는 단서가 있다. 그러나 `41237`의 `*4`는 보라색을 가리키므로 두 자료만으로 번호와 색의 전역 대응을 확정할 수 없다. 화면별 스타일, 오래된 테스트 내용 또는 잘못된 데이터 등은 모두 가설이다.
- `0`, `1`, `2`, `3`, `4`, `5`, `6`, `8`이 영어 자료에서 관찰된다. `8`은 `28051`의 `{*8Shift}`에 등장하지만 키 입력 토큰이라고 단정할 수 없다. `39651`, `41095`, `46692`, `47551`은 각각 닫는 괄호가 없는 독립 조각이다.
- `2685`의 중국어 `{*120分钟}`는 다른 언어의 `{*1 20 minutes}`와 비교하면 `*1` 뒤의 표시 문구가 `20分钟`인 해석이 유력하다.
- 강조할 어구와 횟수는 번역에 따라 바뀐다. 예를 들어 `17783` 독일어는 영어에 없는 광선 공격 강조를 추가했고, `58669` 이탈리아어는 두 강조 구간을 한 구간으로 합쳤다. **개수가 다르다는 이유만으로 자동 보정하지 않는다.**

### `{LINE_...}`: 행과 문단의 배치 후보

- 영어에서 `LINE_LEFT`, `LINE_CENTER`, `LINE_SPACE`, `LINE_INDENT`, `LINE_BULLET`, `LINE_BULLET_INDENT`, `LINE_NEXT_PAGE`가 확인된다. 이름과 문맥상 왼쪽/가운데 정렬, 간격, 들여쓰기, 글머리 및 페이지 전환으로 추정되지만 정확한 픽셀·줄바꿈 동작은 미확인이다.
- `51803`의 개발용 본문은 `LINE_SPACE` 다음에 빈 줄이 있다고 기술하고 `LINE_CENTER` 다음을 가운데 정렬이라고 기술한다. 이는 의미 추정을 뒷받침하지만 실제 렌더링 확인을 대신하지 않는다.
- `4171`은 영어의 두 `LINE_INDENT`가 중국어와 러시아어에서는 `LINE_LEFT`다. `57708` 일본어는 `LINE_SPACE`를 추가하고, `23218` 스페인어는 토큰 대신 실제 빈 줄을 사용한다. 차이 자체는 존재하나 양쪽이 똑같이 보인다고 증명되지는 않았다.
- 독일어 `3076`, `49486`의 `{LINE_INCIDENT}` 3개는 다른 언어와 같은 목록 위치의 `{LINE_INDENT}`에 대응한다. `INCIDENT`가 데이터 전체에서 이 세 번만 관찰되므로 오타 가능성이 높지만 게임 엔진의 허용 토큰 여부는 미확인이다.

## 전체 집계

## 작업 지침과 한계

1. 번역 시 인자의 번호와 출현 횟수를 우선 보존하고, 한국어 어순에 맞게 이동한다. 의미상 반복을 줄이더라도 동적 정보가 사라지는지 먼저 확인한다.
2. `{*N...}` 안의 표시 문구를 번역하되, 번호와 범위는 해당 문맥에서 유지한다. 문장 재구성으로 강조 범위나 횟수를 바꾸려면 원문과 화면을 함께 검토한다.
3. `LINE`은 기본적으로 보존한다. 언어별 차이가 실제로 있으나 화면 결과를 검증하지 않은 채 영어 또는 중국어에 일괄 동기화하지 않는다.
4. 조각 레코드는 균형 검사에서 예외로 다룬다. `8656` 한국어의 여분 `}`는 조사 대상으로 남긴다. 이번 검수에서는 번역 CSV를 수정하지 않았다.
5. `tools/loc_toolset/unpacker_default.py`와 `repacker_default.py`는 텍스트를 디코딩·인코딩할 뿐 이 문법을 해석하지 않는다. 게임 화면이나 실제 파서 확인 전에는 렌더링 결과, 색상 팔레트, 조각 결합 방식 및 허용 문법을 확정할 수 없다.
